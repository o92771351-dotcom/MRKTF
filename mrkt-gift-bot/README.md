# MRKT Gift Monitor Bot

Telegram-бот мониторинга коллекционных подарков: отслеживает предложения (листинги)
на маркетплейсе, находит **монохромные** варианты по фильтрам пользователя, оценивает
**выгоду** цены относительно ориентира, считает **релевантность 0…100** и присылает
карточки лотов в Telegram.

---

```text
  - Big Year | Industrial | Gunship Green | 3.99 TON | id=b6ee1298-dca8-47f7-8265-7697eeb7e1ac
  - Candy Cane | Sugar Crush | Light Olive | 4.00 TON | id=3c421f24-4961-4b6c-a538-4a5761a8c18c
```

`GET /gifts/collections` → 134 коллекции, `POST /gifts/saling` → реальные лоты
с ценами в nanoTON, цветами фона и ключами картинок; курсорная пагинация работает.

Особенности живого API, найденные при проверке и учтённые в коде:

* все четыре массива фильтра (`collectionNames`, `modelNames`, `backdropNames`,
  `symbolNames`) **обязательны** в теле запроса — иначе `HTTP 400` с валидацией;
* пустой `collectionNames` даёт `{"gifts": [], "total": 0}`: «весь рынок» одним
  запросом не отдаётся, поэтому бот перебирает коллекции
  (лимит `MRKT_MAX_COLLECTIONS`, по умолчанию 12 за цикл — защита от 429);
* `modelStickerThumbnailKey` — **относительный** ключ (`gifts/stickers/thumbnails/<hex>.webp`),
  полный URL = `MRKT_CDN_URL` + ключ; файлы в WebP, для Telegram конвертируются в JPEG;
* токен принимается в заголовке `Authorization` **без** префикса `Bearer`
  (схема `raw`), плюс `Cookie: access_token=<token>`; при смене схемы API клиент
  перебирает оба варианта автоматически.

Демо-режим (`SOURCE=demo`) сохранён: он не требует токена и полезен для проверки
интерфейса. Все его карточки помечаются `⚠️ ТЕСТОВЫЕ ДАННЫЕ`.

### Историческая справка: почему раньше было «не подключено»

Публичного документированного API у MRKT нет. Все маршруты данных закрыты авторизацией
пользовательской сессией мини-приложения:

| Запрос (без валидного токена) | Результат проверки |
|---|---|
| `POST https://api.tgmrkt.io/api/v1/gifts/saling` | **HTTP 404** без токена / **HTTP 200** с токеном |
| `GET https://api.tgmrkt.io/api/v1/gifts/collections` | **HTTP 404** |
| `POST https://api.tgmrkt.io/api/v1/auth` | **HTTP 403** `Forbid 1` |
| `POST https://api.tgmrkt.io/api/v1/feed` | **HTTP 404** |
| `GET https://contest.tgmrkt.io/contest/v1/gifts-collections` | **HTTP 401** + traceId (нужен свой `X-CONTEST-KEY`) |
| `https://www.mrkt.land/…` (маршруты подарков) | **HTTP 404** (это витрина CS2, не подарки) |

Доступ к данным возможен **только с токеном пользовательской сессии**
мини-приложения @mrkt. Как его получить за пару минут — раздел
[«Быстрое получение токена MRKT»](#5-быстрое-получение-токена-mrkt).

Выдавать демо-данные за реальные бот не умеет — маркировка зашита в доменную
модель (`Listing.is_test_data`) и проставляется на всех уровнях: карточка,
подпись к фото, `/status`, `/diag`, логи.

Единственный **проверенный рабочий** внешний источник в проекте — публичный API
**@GiftChanges** (`https://api.changes.tg`): он отвечает без ключей и даёт цвета
фонов, PNG моделей и редкости подарков. Используется для определения монохромности
и для картинок в карточках.

> **Атрибуция (обязательное условие использования api.changes.tg).**
> Данные об изображениях, цветах фонов и редкости подарков предоставлены публичным
> API **@GiftChanges** — https://api.changes.tg
> Кредит показывается в боте командами `/credits` и `/about`, в `/help`, в footer
> `/start` и в этом README. Поддержка проекта-источника: `giftchanges.ton`,
> `t.me/boost/GiftChanges`.

### Ключевые решения

1. **Источник данных — интерфейс, а не конкретный API.**
   `app/sources/base.py:ListingSource` — ABC с методами `status()`, `fetch()`,
   `collections()`, `models()`, `backdrops()`, `symbols()`, `get_image()`, `close()`.
   Реализации: `DemoSource` (по умолчанию), `MrktSource` (реальный API, ждёт токен).
   Замена источника — одна строка в `app/sources/factory.py:build_source()`,
   остальной код (фильтры, ранжирование, уведомления) не меняется.

2. **Жёсткие фильтры работают до ранжирования.**
   `matching.apply_hard_filters()` отбрасывает лоты, которые не проходят по
   обязательным критериям (коллекция, цена, атрибуты, порог монохрома, порог
   выгоды). Ранжирование видит только выживших — оценка не «вытягивает» лот,
   который пользователь запретил.

3. **Оценка выгоды опирается на наблюдаемые данные, а не на догадки.**
   Анкер выбирается по приоритету достоверности: флор по тем же атрибутам из API →
   медиана аналогов с теми же атрибутами в нашем кэше → медиана лотов коллекции →
   флор коллекции. Если аналогов меньше `VALUE_MIN_COMPARABLES`, оценка помечается
   `ненадёжно` или не показывается вовсе.

4. **Релевантность объяснима и настраивается.**
   `score = 100 · Σ(wᵢ·cᵢ) / Σ(wᵢ)` по пяти компонентам. Пользователь меняет веса
   командой `/weights` (сохраняются в БД), бот показывает разложение оценки
   в карточке и по кнопке «почему этот лот».

5. **Дедупликация на уровне (пользователь, фильтр, лот).**
   Повторно лот приходит только при снижении цены ≥ `RESEND_PRICE_DROP_PERCENT`
   или после возвращения на рынок спустя `RESEND_AFTER_HOURS`.

6. **Мультипользовательская изоляция.** Все таблицы содержат `user_id`, репозиторий
   всегда фильтрует по нему; `sent_listings` уникален по `(user_id, filter_id, listing_key)`.

## 3. Быстрый старт

### Требования

* Python **3.11+** (разработка и проверка — 3.13)
* Токен бота от **@BotFather**
* Доступ в интернет для `api.telegram.org` и `api.changes.tg`

### Локально

```bash
cd mrkt-gift-bot
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt

cp .env.example .env
# отредактируйте .env: минимум BOT_TOKEN (SOURCE=demo оставьте как есть)

python main.py --check     # диагностика источника данных (бот не запускается)
python main.py             # запуск
```

### В Docker

```bash
cp .env.example .env       # заполнить BOT_TOKEN
docker compose up -d --build
docker compose logs -f bot

# диагностика внутри контейнера
docker compose run --rm bot python main.py --check

# остановка (30 c на корректное завершение цикла мониторинга)
docker compose stop
```

Данные (SQLite, кэш изображений) и сессии Telegram лежат в volume
`bot-data` и `bot-sessions`, поэтому пересборка образа их не теряет.

```text
  - Paper Crane | Mint | Smoke | 9.04 TON | id=demo-00081
@GiftChanges:    доступен

Источник данных в порядке.
```

Код возврата `--check` — число обнаруженных проблем (`0` = всё в порядке),

### Шаг 4. Запустить и поговорить с ботом

```bash
python main.py
```

1. `/start` — бот покажет источник данных и **честно предупредит**, если он демо.

   атрибуты, монохром, пороги) либо «Создать быстро» с последующей правкой полей.
3. `/search 5` — немедленный ручной прогон по включённым фильтрам.
4. `/status` — состояние мониторинга, источника, последние циклы, счётчики.
5. `/weights` — подстройка формулы под себя.

## 5. Быстрое получение токена MRKT

Токен выдаёт приватный `POST /auth` на `initData` — подписанную Telegram строку
мини-приложения. Три способа, от самого быстрого к самому автономному.

### Способ A — из DevTools за 2 минуты (быстрый, руками)

1. **Telegram Desktop** (Windows/Linux/macOS) → [@mrkt](https://t.me/mrkt) →
   запустить мини-приложение.
2. В окне мини-приложения: правый клик → **Inspect**
   (или `Ctrl+Shift+I` / `Cmd+Opt+I`) → вкладка **Network**.
3. Кликните любой запрос к `api.tgmrkt.io` → **Request Headers** →
   `Authorization` (или `Cookie: access_token=…`).
4. Скопируйте значение **целиком** и вставьте в `.env`:
   ```ini
   SOURCE=mrkt
   MRKT_TOKEN=55e429b6-30ba-41d0-b58e-8843706a51eb   # пример формата
   ```
5. Проверьте, не выходя из терминала:
   ```bash
   python main.py --token --probe-token "ВАШ_ТОКЕН"
   # ✅ Токен принят: HTTP 200, схема «raw». токен рабочий, выдача получена
   python main.py --check      # теперь уже с SOURCE=mrkt из .env
   ```

> Рабочий токен выглядит как UUID и принимается в заголовке `Authorization`
> **без** префикса `Bearer` (клиент при необходимости сам переберёт обе схемы).

### Способ B — одной командой (автономный, нужен telethon)

```bash
pip install telethon
```

В `.env` пропишите `TG_API_ID` и `TG_API_HASH` с
[my.telegram.org](https://my.telegram.org) → *API development tools*, затем:

```bash
python main.py --token                 # получить токен и проверить его
python main.py --token --write-env     # …и сразу записать в .env (MRKT_TOKEN + SOURCE=mrkt)
```

При первом запуске telethon спросит телефон и код из Telegram — создастся файл
сессии в `TG_SESSION_WORKDIR` (по умолчанию `./sessions`, в Docker — volume
`bot-sessions`). Дальше токен обновляется автоматически: как только MRKT
ответит 401/403/404, клиент сам перезапросит `initData` и продолжит работу.

**Используйте отдельный («служебный») Telegram-аккаунт**: вход выполняется от
имени аккаунта, а площадка может расценить автоматизацию как нарушение своих
условий. Файл сессии — секрет, не коммитьте его (он в `.gitignore`).

### Способ C — Contest API (только флор-цены)

Если команда MRKT выдаст вам `X-CONTEST-KEY` (UUID), эндпоинт
`https://contest.tgmrkt.io/contest/v1/gifts-collections` отдаёт флор-цены
коллекций server-to-server, без пользовательской сессии. Полный список лотов
он **не** даёт — только данные для анкера оценки выгоды.

### Куда девать токен в проде

Токен живёт недолго (по наблюдениям — от нескольких часов до суток). Поэтому:

* в Render/контейнере держите его в переменной окружения `MRKT_TOKEN`
  (**не** в файле и не в образе);
* для автообновления добавьте `TG_API_ID`, `TG_API_HASH` и диск/volume для
  `sessions/` — тогда токен будет перевыпускаться сам (способ B);
* `python main.py --token --probe-token "…"` — быстрая проверка «жив ли токен»,
  ничего не записывает и не печатает токен целиком (только маску).

## 5b. Деплой на Render за 10 минут

Бот работает через **long polling**, поэтому нужен **Background Worker**,
а не Web Service: HTTP-порта нет, и Render не будет ждать входящих запросов.

### Вариант 1 — Blueprint (рекомендуется)

1. Запушьте каталог проекта в GitHub/GitLab. **Проверьте, что `.env` не попал
   в репозиторий** (он в `.gitignore`; секреты задаются только в панели Render).
2. Render → **New +** → **Blueprint** → выберите репозиторий → **Apply**.
   Файл `render.yaml` уже описывает worker, диск и все переменные.
3. В созданном сервисе заполните два секрета: `BOT_TOKEN` и `MRKT_TOKEN`.
4. **Manual Deploy → Deploy latest commit** и смотрите Logs.

### Вариант 2 — руками

1. **New +** → **Background Worker**.
2. Подключите репозиторий; **Root Directory** = каталог проекта.
3. **Runtime: Docker** (образ собирается из `Dockerfile`, команда `python main.py`).
4. **Plan: Starter** — Background Worker на free-плане недоступен; free-план
   к тому же засыпает без HTTP-трафика, что для поллинга означает пропуск событий.
5. **Disk**: mount path `/app/data`, 1 GB — иначе SQLite и история отправок
   будут сброшены при каждом деплое.
6. **Instances: 1**. Два воркера с одним `BOT_TOKEN` будут перехватывать
   обновления друг у друга (Telegram отдаёт каждый update только одному
   получателю).
7. Добавьте переменные окружения (список ниже) → **Create Background Worker**.

### Переменные окружения — минимальный набор

| Переменная | Значение | Зачем |
|---|---|---|
| `BOT_TOKEN` | токен от @BotFather | **обязательно**, иначе бот не стартует |
| `SOURCE` | `mrkt` | включить реальные данные (по умолчанию `demo`) |
| `MRKT_TOKEN` | ваш токен (UUID) | доступ к API MRKT |
| `DATABASE_URL` | `sqlite+aiosqlite:////app/data/bot.db` | SQLite на диске (4 слэша = абсолютный путь) |
| `DATA_DIR` | `/app/data` | каталог данных |
| `CACHE_DIR` | `/app/data/cache` | кэш картинок |
| `ALLOWED_USER_IDS` | ваши Telegram ID через запятую | закрыть бота от посторонних |
| `ADMIN_USER_IDS` | ваш ID | доступ к `/diag` |
| `LOG_LEVEL` | `INFO` | `DEBUG` — при отладке источника |

Всё остальное уже имеет рабочие значения по умолчанию (см. `.env.example`
и `render.yaml`, где перечислены 36 переменных с комментариями). Лишние
переменные окружения Render (`RENDER_EXTERNAL_URL`, `PORT` и т. п.) бот
игнорирует — `extra="ignore"` в `Settings`.

### Если хотите PostgreSQL вместо SQLite

1. Создайте **New +** → **PostgreSQL** в том же регионе.
2. `DATABASE_URL` = `postgresql+asyncpg://…` — возьмите **Internal Database URL**
   (не External: внутренний адрес быстрее и не торчит наружу).
3. `asyncpg` уже есть в `requirements.txt` — пересоберите образ.

### Проверка после деплоя

В логах Render должно быть:

```text
Источник данных: mrkt · доступен=True · тестовые данные=False · MRKT отвечает: …
Бот @ваш_бот (id=…) запущен
Мониторинг запущен: источник=mrkt, тик=20 c
```

Если видите `HTTP 404 и токен не задан` или `токен MRKT не принят, истёк` —
токен не доехал до контейнера или истёк: обновите `MRKT_TOKEN` в Environment
(Manual Deploy не нужен, воркер перезапустится сам). Быстрая проверка локально:
`python main.py --token --probe-token "…"`.

### Ограничение Render, о котором стоит знать

Фоновый воркер перезапускается при каждом деплое, а `MRKT_TOKEN` живёт часы.
Без автообновления (способ B) токен придётся периодически менять руками.
С автообновлением воркеру нужны `TG_API_ID`, `TG_API_HASH` и диск для
`/app/sessions` (добавьте второй disk или храните сессию в том же `/app/data`).

## 5c. Как устроен клиент MRKT

Клиент реализован в `app/sources/mrkt.py` и включает:

* авторизацию заголовками `Authorization: Bearer <token>` **и**
  `Cookie: access_token=<token>`, плюс `Origin`/`Referer: https://cdn.tgmrkt.io/`
  и браузерный User-Agent;
* автоматический перебор схемы авторизации (raw ↔ bearer) при `401/403/404`;
* `POST /gifts/saling` с телом `collectionNames[]`, `modelNames[]`, `backdropNames[]`,
  `symbolNames[]`, `ordering`, `lowToHigh`, `minPrice`, `maxPrice`, `query`,
  `count` (≤ 20), `cursor` — пагинация до `MRKT_MAX_PAGES`;
* троттлинг (`MRKT_REQUEST_DELAY`), экспоненциальный backoff на `5xx`/сеть,
  уважение `Retry-After` на `429`;
* нормализацию полей ответа в `Listing` (цены в nanoTON → `price_nano`,
  редкости в промилле, четыре цвета фона, `modelStickerThumbnailKey` как картинка);
* вывод комиссии из пары `salePrice` / `salePriceWithoutFee`;
* отдельный бюджет повторов для сетевых ошибок и для восстановления авторизации
  (чтобы `MRKT_MAX_RETRIES` не превращался незаметно в «×4»);
* фатальные ошибки (`SourceAuthError`, `SourceRateLimitError`) пробрасываются наверх:
  монитор не «молча пустой», а сообщает причину в `/status` и `/diag`.

### Где взять `MRKT_TOKEN`

Пошагово — в разделе [«5. Быстрое получение токена MRKT»](#5-быстрое-получение-токена-mrkt):
DevTools за 2 минуты, либо `python main.py --token --write-env` через служебную
Telegram-сессию (telethon, `TG_API_ID`/`TG_API_HASH`).

Технически авто-вход выполняет `app/sources/mrkt_auth.py`:
`RequestAppWebView(peer=@mrkt, InputBotAppShortName(short_name="app"))` →
`tgWebAppData=` → `POST /auth` → `{"token": …}`. Токен кэшируется и
перезапрашивается при 401/403/404.

Проверка: `python main.py --check` → строка `Источник: mrkt (mrkt)`,
`Тестовые данные: нет`. Если увидите `HTTP 404 и токен не задан` или
`токен MRKT не принят, истёк` — токен не задан/истёк, а не сломан клиент.

### Ссылка в кнопке «Открыть предложение»

Публичного deep-link на конкретный лот MRKT **не обнаружено**: фронтенд строит
ссылки из поля `inGameLink`, которое отдаёт только авторизованный `GET /me`.
Поэтому:

* если у лота есть `url` от источника — используется он;
* иначе — `MRKT_LINK_TEMPLATE` (по умолчанию `https://t.me/mrkt/app`), а в карточке
  честно написано: «публичная ссылка на конкретный лот не подтверждена» + ID лота;
* в шаблоне работают плейсхолдеры `{id} {collection} {model} {backdrop} {symbol} {number}`.

Как только вы выясните реальный формат ссылки в приложении MRKT (лот → «Поделиться»
→ скопировать ссылку), подставьте его в `MRKT_LINK_TEMPLATE` — карточки начнут
открывать конкретный лот.

### Contest API (опционально, для флор-цен)

`https://contest.tgmrkt.io/contest/v1/gifts-collections` с заголовком
`X-CONTEST-KEY: <UUID>` — server-to-server доступ к флор-ценам коллекций.
Ключ выдаёт команда MRKT по запросу. Без ключа эндпоинт отвечает `401`.
В коде предусмотрен как дополнительный анкер для оценки выгоды.

## 6. Что нужно для реальных данных и ограничения интеграции

| Ограничение | Следствие | Что сделано в коде |
|---|---|---|
| Нет публичного API MRKT | Данные нельзя получить анонимно | Интерфейс `ListingSource` + демо-источник с явной маркировкой |
| Токен привязан к пользовательской сессии мини-приложения | Токен истекает за часы; нужен живой аккаунт | Авто-обновление через Telethon, перебор схем авторизации, внятная ошибка в `/status` |
| Агрессивные лимиты частоты (`429`) | Массовый опрос невозможен | Троттлинг, `count ≤ 20`, `MRKT_MAX_PAGES`, backoff с учётом `Retry-After` |
| Нет подтверждённого deep-link на лот | Кнопка ведёт в приложение, а не в лот | `MRKT_LINK_TEMPLATE` + честная подпись в карточке + ID лота |
| Формат ответа может меняться без уведомлений | Парсер может «ослепнуть» | Нормализация принимает альтернативные имена полей (`saleId`, `price`, `imageUrl`, `createdAt`), неизвестные поля складываются в `extra` |
| Неполная выдача (обрыв пагинации) | Нельзя считать пропавшие лоты проданными | `FetchResult.complete`; `mark_missing_inactive` вызывается только при полной выдаче |
| Комиссия площадки документирована неоднозначно | Выгоду легко посчитать неверно | Комиссия выводится эмпирически из `salePrice` vs `salePriceWithoutFee`; анкер — цена предложения (то, что платит покупатель) |
| Нет данных о фактических сделках | «Выгода» = сравнение с текущим предложением | Обязательный дисклеймер в каждой карточке и в `/help` |
| Используется сторонний API @GiftChanges | Требуется видимая атрибуция | Кредит в `/credits`, `/about`, `/help`, `/start`, README; отключается `CHANGES_API_ENABLED=false` |

**Альтернатива с официальным статусом.** Telegram предоставляет MTProto-методы
`payments.getStarGifts` и `payments.getResaleStarGifts(gift_id, attributes, offset,
limit, sort_by_price|sort_by_num)`, возвращающие `starGiftUnique{slug, num, owner_id,
attributes, resell_amount}` со ссылкой `https://t.me/nft/<slug>`; комиссия перепродажи —
в конфиге `ton_stargift_resale_commission_permille`. Это документированный, стабильный
источник данных о перепродаже звёздных подарков, но он работает через
пользовательский MTProto-клиент (Telethon/Pyrogram), отдаёт только Telegram-маркет
(не MRKT) и поддерживает лишь polling. В этом MVP он не реализован — интерфейс
`ListingSource` позволяет добавить его как `app/sources/telegram_mtproto.py`
без изменения остального кода.

## 7. Как это считает бот

### 7.1. Монохромность (`app/filters/monochrome.py`)

Четыре уровня доказательств, от надёжных к ненадёжным:

| Метод | Источник | Уверенность |
|---|---|---|
| `backdrop_colors` | `backdropColors{Center,Edge,Text,Symbol}Color` в листинге MRKT (RGB-int) | high |
| `changes_api_colors` | `api.changes.tg` → `/gift/:gift` или `/backdrop/:gift/:backdrop/info` (`hex{centerColor,edgeColor,patternColor,textColor}`) | high/medium |
| `image` | HSV-статистика по картинке (`/model/:gift/:model.png?size=…`, `/original/:id.png`, `modelStickerThumbnailKey`) | medium |
| `name` | эвристика по названию (`noir`, `chalk`, «серый»…) | **low** — всегда с явной пометкой |

* Цвет текста (`textColor`) **исключён** из статистики artwork: он бывает ярким
  у монохромного подарка и ломает определение тона.
* Тон (`dark` / `light`) работает как **множитель** серого балла, а не как слагаемое:
  `gray · (0.15 + 0.85 · tone)`. Иначе чёрный подарок набирал бы ~70 баллов в
  режиме «светлый».
* Итог: балл 0…100, метод, уверенность — всё это показывается в карточке.
* Определение **только по названию** используется, когда других доказательств нет,
  и всегда помечается `низкая уверенность` + предупреждение в карточке.

### 7.2. Выгода (`app/value.py`)

```
diff_percent = (benchmark − price) / benchmark · 100        (>0 — лот дешевле ориентира)
```

Приоритет анкера: `exact_floor` (флор по тем же атрибутам из API) →
`peers_exact` (медиана аналогов `collection|model|backdrop|symbol` из кэша) →
`peers_collection` (медиана лотов коллекции) → `collection_floor`.

В карточке всегда видно: цену лота, анкер и его происхождение, число аналогов,
разницу в %, уверенность. При `comparables < VALUE_MIN_COMPARABLES` оценка
помечается ненадёжной; если анкера нет — бот пишет «выгода не рассчитана»,
а не придумывает число. Дисклеймер «не гарантия прибыли» присутствует всегда.

### 7.3. Релевантность (`app/ranking.py`)

```
score = 100 · Σ(wᵢ · cᵢ) / Σ(wᵢ),   cᵢ ∈ [0, 1]
```

| Компонент | Что измеряет | Вес по умолчанию |
|---|---|---|
| `match` | доля совпавших критериев фильтра | 0.25 |
| `monochrome` | балл монохромности / 100 | 0.25 |
| `value` | ожидаемая выгода (насыщается на пороге) | 0.25 |
| `confidence` | надёжность данных (монохром + выгода + аналог) | 0.15 |
| `freshness` | возраст лота, `exp(−ln2 · age / RANK_FRESHNESS_HALF_LIFE_HOURS)` | 0.10 |

Если компонент посчитать нельзя, его вес **перераспределяется** между остальными —
лот не тонет из-за отсутствия данных. Веса настраиваются глобально (`RANK_WEIGHT_*`)
и персонально (`/weights`, хранятся в БД). Разложение оценки показывается в карточке
и по кнопке «почему этот лот».

### 7.4. Повторные уведомления (`app/pipeline.py:decide_send`)

| Ситуация | Решение (`DecisionReason`) |
|---|---|
| Лот ещё не отправлялся этому пользователю по этому фильтру | `new` → отправить |
| Цена снизилась ≥ `RESEND_PRICE_DROP_PERCENT` | `price_drop` → отправить, в карточке пометка «снижение цены» и величина снижения |
| Лот исчезал и снова в продаже спустя ≥ `RESEND_AFTER_HOURS` | `returned` → отправить |
| Изменились атрибуты лота (модель/фон/символ/номер) | `changed` → отправить |
| Цена выросла или не изменилась, атрибуты те же | `duplicate` → молчать (обновляется только «время последнего наблюдения») |

| `/history` | что уже было отправлено по фильтрам |
| `/credits`, `/about` | источники данных и обязательная атрибуция @GiftChanges |
| `/diag` | диагностика источника (только `ADMIN_USER_IDS`) |

Фильтры редактируются inline-кнопками: каждое поле — отдельная кнопка, значение
вводится одним сообщением, «-» сбрасывает поле (для порогов — к значению по
умолчанию). Меню монохрома переключает режим (`gray/dark/light/custom`), порог
балла, насыщенность, целевой тон и допуск, а также разрешает/запрещает
эвристику по названию.

## 10. Переезд на PostgreSQL

SQLite выбран для MVP (один файл, ноль администрирования). Переход:

1. `pip install asyncpg` (или раскомментируйте строку в `requirements.txt`).
2. В `.env`:
   ```ini
   DATABASE_URL=postgresql+asyncpg://bot:secret@localhost:5432/mrkt_bot
   ```
3. `docker compose --profile postgres up -d --build`.

Схема создаётся при старте (`Database.create_all()`), код не содержит
SQLite-специфики: все `DateTime` хранятся как UTC и нормализуются через
`app.domain.ensure_aware()`. Для продакшена дополнительно рекомендуется
миграционный инструмент (Alembic) — схемы в `app/db/models.py` уже версионируемы.

## 11. Безопасность

* Секретов в репозитории нет: токен бота, токен MRKT, `TG_API_ID/HASH` — только
  из окружения; `.env` в `.gitignore` и `.dockerignore`.
* `ALLOWED_USER_IDS` ограничивает доступ; `ADMIN_USER_IDS` — доступ к `/diag`.
* В контейнере процесс работает под non-root пользователем `botuser` (UID 10001).
* Если пользователь заблокировал бота (`TelegramForbiddenError`), чат помечается
  в `DeliveryStats.blocked_chats` и дальнейшие отправки в него не выполняются.
* Все пользовательские строки экранируются (`html.escape`) перед вставкой в
  HTML-разметку карточек — инъекция разметки через название коллекции невозможна.
* Ошибки источника не раскрывают токен: в логах и `/status` — только код ответа
  и усечённое тело.

## 12. Ограничения ответственности

Бот **не покупает** подарки и не совершает сделок — это инструмент мониторинга.
Оценка выгоды сравнивает цену лота с текущими ценами предложения, а не с фактами
сделок; она не является гарантией прибыли или инвестиционной рекомендацией.
Демо-источник выдаёт синтетические данные, которые всегда помечены.
Использование приватного API MRKT может нарушать условия сервиса площадки —
убедитесь, что у вас есть право на такой доступ, прежде чем переключать
`SOURCE=mrkt`.
